# 还原说明：基于激光雷达的自主导航迎宾机器人

> 本文说明「用什么材料、还原出了什么、哪些是确认的、哪些还没验证」。
>
> 本项目分两个阶段：第一阶段只有交互元数据（无硬件型号、无协议），做的是
> Python 差速轮控制骨架，即 `src/robot_recon/`，说明见
> [robot-recon-skeleton.md](robot-recon-skeleton.md)；第二阶段拿到了方案报告、
> PPT、导航 SDK 与雷达 SDK，据此按**实物材料**重建了 Android + ROS2 + 后台三端，
> 也就是本仓库的主体。两个阶段不冲突，后者在硬件控制链路上取代前者的推测部分。
>
> 第一阶段的服务器侧取证材料（对话元数据、调查记录，含主机地址与账号信息）
> 属于调查档案而非源码，未上传到本仓库。

## 1. 证据分级

| 结论 | 依据 | 级别 |
|---|---|---|
| 底盘是旗瀚 Sanbot S1，导航走 `com.sanbot.map.MapClient`（jar 1.5.2） | `20191118/navigationSDK` 中的 demo 源码、`Map_1.5.2.jar`、`.doc` 协议文档 | 实测（反编译/文档） |
| 地图/点位来自系统服务，App 只读；地图是 pgm 像素 + `invertMap`/`setPixels` 渲染 | 同上，文档 1.5 第 4 章 | 实测 |
| `openNavigation/navigationTo/cancelNavigation/adjustPosition` 都是**阻塞**调用 | 文档明确标注 `(阻塞)`，demo 用 `HandlerThread` 规避 | 实测 |
| 导航状态码含义（0x00~0x3b）、错误码自动取消延时 | 文档第 5 章 + demo `ExplainCode.java` | 实测 |
| 雷达是 RPLIDAR A1M8，115200bps，0.15~12m，1° 分辨率 | 报告 2.2/3.1、PPT 第 4 页、`雷达SDK/` 手册与数据表 | 实测 |
| SLAM 用 ROS2 Jazzy + slam_toolbox，`/scan` 8.7Hz，VMware Ubuntu 24.04 | PPT 第 5、10、11 页 | 用户陈述（PPT 自述） |
| 机器人端 UI 是 Android + WebView(H5)，有 `ChassisAdapter`/`RobotJsBridge` 桥接层 | PPT 第 10 页「机器人端」 | 用户陈述 |
| 后台是 Node.js 零依赖 + 手写 xlsx | PPT 第 10 页、第 8 页 | 用户陈述 |
| 语音 ASR/TTS、人脸识别、访客台账、企业名录 | PPT 第 7、8 页 | 用户陈述（本次未还原实现） |
| 雷达 USB 供电不足导致真机航点导航未验证 | PPT 第 11 页「进行中」 | 用户陈述 |

**噪音提示**：方案报告（docx）里写的是「基于 ROS2 + slam_toolbox，无需里程计」，
而 PPT 又说「里程计 + 激光匹配定位」。两者矛盾，本工程按 PPT 为准（需要 `/odom`），
因为 slam_toolbox 的 `odom_frame` 是必需参数。若真机确实没有里程计，就在
`chassis_bridge` 里把 `/odom` 设成恒等变换（有现成参数可改）。

## 2. 还原出的系统

```
┌──────────────────── Android（Sanbot S1）────────────────────┐
│  H5 控制台（assets/www）                                     │
│      ↕ NativeBridge(JsBridge)                                │
│  BotController ── NavGateway ── Map_1.5.2.jar ── 系统导航服务 │
│      │             └─ MapRepository（地图/点位渲染）          │
│      ├─ ObstacleGuard ← RpLidarA1 ← USB 串口（雷达）          │
│      ├─ ChassisAdapter（真机 / 仿真）                        │
│      ├─ SpeechHelper（TTS 播报）                             │
│      └─ BridgeServer:9001 （行 JSON）                        │
└───────────────────────────┬─────────────────────────────────┘
                            │ WiFi
┌───────────────────────────┴──── ROS2（VMware Ubuntu）────────┐
│  chassis_bridge  ←→  /cmd_vel_raw /odom /TF                   │
│  scan_safety     ←   /scan、/cmd_vel                          │
│  slam_toolbox（mapping / localization）                        │
│  nav2（NavFn 全局 + DWB 局部）                                │
│  waypoint_manager（命名点位 → NavigateToPose）                │
└──────────────────────────────────────────────────────────────┘
                            │
┌───────────────────────────┴──── 运营后台（Node.js 零依赖）────┐
│  REST：点位 / 任务 / 访客 / 知识库 / 统计 / xlsx 导出          │
└──────────────────────────────────────────────────────────────┘
```

### 关键还原点（都是当年卡住的地方）

1. **阻塞接口不能放主线程**：`navigationTo` 会阻塞到服务回包，demo 里全部丢到
   `HandlerThread`。`NavGateway` 复刻了这一点，且把回包统一转成结果码+中文。
2. **地图数据只能转换一次**：`MapHelper.invertMap` 是原地修改，重复调用会把
   可走区域和障碍翻反。`MapRepository` 做了缓存，只在 `mapChanged()` 时重载。
3. **`libMapHelper.so` 只有 32 位 ARM**：64 位设备直接 `UnsatisfiedLinkError`，
   且发生在 `Application` 静态块里，崩溃日志看不出原因。`App` 改为容错加载，
   `MapPixelConverter` 按文档语义提供纯 Java 等价实现。
4. **单位换算**：SDK 位姿是地图像素，`chassis_bridge` 用 `map_resolution`
   （默认 0.05 m/px）换算，并把图像 y 轴翻转成 ROS 右手系。
5. **1Hz 状态推送 + 无速度环**：`/cmd_vel` 必须加看门狗（0.5s 无指令即刹车），
   否则上位机崩了机器人会继续走。
6. **雷达需要独立的安全闸**：nav2 的代价地图依赖定位，定位漂了看不到行人；
   `scan_safety` 直接用原始 `/scan` 判前后扇区，是最后一公里兜底。

拼写级错误。**这是本次交付最大的未验证项，不要当成已跑通。**

## 5. 待确认 / 未还原

| 编号 | 缺口 | 影响 | 建议 |
|---|---|---|---|
| G1 | `WheelMotionManager` 三个 bean 的构造签名（反编译看到 `(BIIIB)V` 等非常规形态） | 无法用真正的速度环控制底盘，只能用导航 SDK 的“虚拟目标点”近似 | 在真机上用 `javap -p` 或 Android Studio 的 jar 反编译确认后再切换 |
| G2 | 雷达在真机的供电/枚举稳定性 | PPT 已注明「USB 供电待补齐」 | 加外供电 USB Hub，或改从底板的 5V 取电 |
| G3 | Sanbot 地图服务里 `resolution` 的实际值 | 若不等于 0.05，导航会系统性偏移 | 启动时读 `Map.getResolution()` 打到日志，回填 `map_resolution` 参数 |
| G4 | 语音 ASR 唤醒词与指令集（PPT 有「带我去 XX」） | 只能键盘/触屏下发 | 接 `SpeechManager.setOnSpeechListener` 做本地关键词解析 |
| G5 | 人脸识别 SDK 与访客登记联动 | 后台有台账，机器人端未接 | 二期 |
| G6 | 自动回充（`SystemManager.doHomeAction`） | 低电量回充未实现 | dsdk 里有 `doHomeAction`，接上即可 |

## 6. 上机顺序（建议）

```bash
# 0) 准备：机器人与上位机同网段，记录机器人 IP
# 1) 装 App（有 Android SDK 的机器上先编译）
cd robot-app && gradle assembleDebug && adb install -r app/build/outputs/apk/debug/app-debug.apk

# 2) 验证 Android 桥接
adb shell "logcat -s BridgeServer BotController LidarSession"
printf '{"cmd":"status"}\n' | nc <机器人IP> 9001

# 3) 上位机建图
cd ros2_ws && colcon build --symlink-install && source install/setup.bash
ros2 launch sanbot_nav mapping.launch.py robot_host:=<机器人IP>

# 4) 保存地图 -> 导航
ros2 run nav2_map_server map_saver_cli -f ~/maps/hotel_map
ros2 launch sanbot_nav navigation.launch.py robot_host:=<机器人IP> map:=~/maps/hotel_map.yaml

# 5) 下发点位
ros2 topic pub --once /sanbot/goal std_msgs/String "{data: 会议室}"

# 6) 后台
cd backend && node server.js   # 打开 http://<IP>:8080
```

## 7. 两条务必先做的事

1. **先跑仿真**：H5 上有「仿真模式」，没有机器人也能验证点位点击 → 状态机 →
   语音文案 → 桥接输出，避免把 UI 问题误判成底盘问题。
2. **先测停机**：上车第一步不是“能不能走到”，而是“能不能立刻停”。
   依次验证：H5 急停按钮、雷达遮挡前方 45cm、拔掉上位机网线（看门狗 0.5s 刹车）。
   三条都过了再调路径。
